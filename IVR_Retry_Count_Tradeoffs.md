# IVR Retry Count — Tradeoffs Register

Companion to `IVR_Retry_Count_PRD.md` (v1.0 · signed off 2026-09-08). Records every decided tradeoff during interview and review passes. Not part of the PRD; kept for later reference so anyone asking *"why did we pick X?"* has the answer without archaeology.

| # | Decision point | Chosen | Rejected options | Why (PM's stated reason) | Date |
|---|---|---|---|---|---|
| 1 | Mechanism for retry: how do we make Exotel dial the same number twice? | **Duplicate the number inside the `numbers` array on our Connect-applet response** — Exotel dials each entry in order and does not dedupe (confirmed by Exotel support: Tanay Puntambekar, Adnan C). | **(a) Re-enable Exotel's account-level "Retry-All" mode** (currently disabled on wiom67) — was ruled out because it fires only on fast/transient failures, not on the no-answer / timeout case we actually want to cover. **(b) `fetch_after_attempt=true`** — Exotel would re-hit our URL after each failed dial for a fresh numbers list — more complexity than needed for a fixed-count retry. | Fully in our control; no Exotel-side config change; matches the semantic the PM proposed and Exotel confirmed as supported. | 2026-09-08 |
| 2 | Scope of the retry knob | **Single global `retry_count` (C-01)** — one scalar applied uniformly to every rollover-list entry across both call directions. | **(a) Per-direction knobs** — `retry_count_customer_initiated`, `retry_count_csp_initiated` for independent A/B testing per direction. **(b) Per-user-type knobs** — primary vs fallback numbers retried differently. | PM steer: "just retries logic, nothing else" — keep the surface minimal for v1. Per-direction / per-user-type can be added later if the single knob proves insufficient. | 2026-09-08 |
| 3 | Default value of C-01 at launch | **1** — every call gets a single retry from day one. | **0** — matches today, silent ship, operator must actively flip to see the lift. | PM answered directly. Rationale is speed-to-impact: the +11pp Sept 2 lift already showed the platform's appetite for these small optimisations. | 2026-09-08 |
| 4 | Success metric shape | **M1 only** — one call-level connect rate, direction split retained as a diagnostic cut on MQ-1 but no dedicated M-id. | Original draft had three metrics: **M1** (call-level), **M2** (customer-initiated), **M3** (CSP-initiated). | PM steer: "Remove M2 and M3." Direction split is a cut inside the same measurement, not a separate success measure. | 2026-09-08 |
| 5 | Guardrails | **G1** (behaviour at C-01 = 0 identical to today) + **G2** (IVR 2.0 functionality preserved — this spec is a pure extension). | Original draft had a third guardrail "**G3 — Runtime-changeable, no deploy**." Also had an original G2 about no early rollover. | PM steer: G1 kept; add "IVR 2.0 preserved" as the second guardrail; drop G3 ("that's a config test case, not a guardrail"); drop old G2 (behaviour implicit in T2/T3 ordering rules). | 2026-09-08 |
| 6 | Whether the 10-entry Exotel platform limit is a Wiom config | **External constraint — not a Wiom parameter.** Referenced in the spec as "Exotel's 10-entry platform cap"; the truncation branch (T4) protects the call, but the number is not a C-id. | Model it as **C-02 — max numbers-array size, fixed at 10 by Exotel**. | PM steer: "Remove C-02, it's the Exotel limit, not ours." Only Wiom-tunable levers deserve a C-id; platform constraints are stated as facts. | 2026-09-08 |
| 7 | Caller scope enforcement | **Informational context only** in §1. The caller eligibility set is IVR 2.0's — including the PIN-authenticated colleague-forwarding case on an unregistered SIM. This spec neither narrows nor widens it. | Draft had a restrictive "**Only two populations qualify: CSP user or customer with an active ticket**" definition with a MUST NOT and a supporting AC. | PM steer: "Unauthorised caller is also allowed as per the IVR 2.0 if he has the PIN. Frame it smartly so that we do not have an acceptance criteria for the things which is already working." | 2026-09-08 |
| 8 | Out-of-range value handling on C-01 | **No AC.** If a value outside {0, 1, 2} is set, implementer default applies. | Draft had **AC-CFG-2** specifying clamping to the nearest in-range value (0 or 2). | PM steer: "AC-CFG-2 — No Need." A runtime knob with a bounded 3-value range does not need a spec-level clamp policy in v1. | 2026-09-08 |
| 9 | Cross-flow coverage in acceptance criteria | **Explicit AC per IVR 2.0 calling path** — AC-WF-1 (in-app CTA / Path 1), AC-WF-2 (dialer + single active ticket / Path 2), AC-WF-3 (dialer + PIN / Paths 3–4), plus AC-WF-4 for the end-to-end rollover journey. | Rely implicitly on the fact that all three paths converge at the Connect-applet fetch, and let a single AC represent the expansion behaviour. | PM steer: "Have AC for all the three flows of IVR Calling... The expansion of the list should work for all the three IVR calling usecases." Explicit ACs make the cross-flow contract testable and unambiguous. | 2026-09-08 |
