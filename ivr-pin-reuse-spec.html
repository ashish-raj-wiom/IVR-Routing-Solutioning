IVR-01 · Change spec · v1.0

Reuse PIN across execution candidates sharing the same ticket_id (RESTORE only)

A single customer can generate multiple RESTORE execution candidates in rapid succession — each new EC gets a fresh PIN and the old EC's PIN is instantly deallocated. Callers with the previous PIN in hand (from SMS, chat, or their memory) enter it and fail. This spec aligns the PIN's lifetime with the ticket_id that the customer already sees, eliminating the churn-driven PIN staleness.

Owner: Ashish Raj (PM, IVR) Service: IVR Scope: ivr_pin_registry allocation logic Status: Draft

Quick check

7-line triage
Problem
Multi-EC RESTORE tickets churn PINs; callers use the stale PIN and the IVR bridge fails.
Evidence
20 of 66 unbridged calls (30%) in Phase-1 cohort 2–7 Jul are attributable to this. 3,107 of 36,873 RESTORE ticket_ids in the last 30 days have ≥ 2 execution candidates (8.4%). One ticket_id has 26 ECs.
Root cause
PIN allocation is scoped to execution_candidate_id, not to ticket_id. New EC → fresh PIN, previous EC's PIN deallocated instantly.
Fix
On new EC allocate, look up prior rows in ivr_pin_registry for the same ticket_id. If found and the PINs are currently free, reuse them. Else, allocate fresh.
Scope
RESTORE only. Non-RESTORE execution candidates do not carry a ticket_id at all, so the reuse lookup naturally has no key to match on for them — the fresh-mint path continues as today.
Frontend
Zero change. Apps and Exotel see the same PIN across ECs — that's the whole point.
Impact
Bridge rate 96.1% → ~97.3% just from this. Kills the churn root cause across Buckets 1 / 2 / 3 of the current RCA.
Part A

What we are changing

The IVR PIN allocation logic. Nothing else moves. No CSP App change, no Customer App change, no CleverTap / SMS change, no cohort-flow change.

A2. Why this change WHAT

Three connected observations:

(1) A single ticket_id can span many execution candidates. When the upstream service creates a new RESTORE execution candidate for a customer, it re-uses the same ticket_id that the customer has been receiving in their SMS / chat. Today IVR treats each execution candidate as a fresh allocation and mints new PINs. The customer's cached credential (from the SMS they received minutes / hours ago) instantly becomes invalid.

(2) The pattern is severe. In the last 30 days, 8.4% of RESTORE ticket_ids have ≥ 2 execution candidates. One ticket_id has 26 ECs across 3 days. In one recorded case, a single customer generated 4 execution candidates for the same ticket_id in 10 minutes, each open for less than a minute. The CSP was calling to bridge, the ticket_id under them was churning, and every PIN they typed was already deallocated by the time the IVR checked it.

(3) The failure signature is unambiguous. 14 of 20 attributable failures in the Phase-1 sample had the caller enter a PIN that exactly matches a prior execution candidate's PIN for the same customer's ticket_id. The remaining 6 have the churn signature but with fragmented / mid-attempt digits. This isn't a UX problem or a comms-discoverability problem — the caller has the right value; the system has moved out from under them.

A3. Solution in one paragraph WHAT

When the IVR receives a new execution candidate to allocate PINs for, it queries ivr_pin_registry for prior rows with the same ticket_id. If found, it reuses the most recent (customer_pin, csp_pin) pair for the new execution candidate — subject to a safety check that neither PIN is currently ALLOCATED to any other execution candidate. Where the ticket_id has no prior rows (first execution candidate for that ticket), a fresh PIN pair is allocated as today. Scope is limited to ticket_type = 'RESTORE', because the data confirms other ticket_types (INSTALL, PICKUP, NBREC) do not exhibit the multi-EC-per-ticket_id pattern.

A5. The delta WHAT

What is expected: One row per atomic change: what changes → before → after → why.
What changesBeforeAfterWhy
PIN allocation lookup on new execution candidate (RESTORE) Allocation flow always mints a fresh pair of PINs (customer_pin, csp_pin) for every new execution_candidate_id, regardless of the ticket_id. Prior EC's PIN is deallocated in the same transaction; the new PIN is inserted. Before minting a fresh pair, allocation queries ivr_pin_registry for rows with the same ticket_id. If any row exists (irrespective of pin_status), the most recent row's (customer_pin, csp_pin) is taken as the candidate pair for reuse. The ticket_id is the identifier the customer already sees on their SMS / chat. Anchoring the PIN's lifetime to ticket_id means the customer's cached credential stays valid across EC transitions for the same ticket.
Safety check: PIN uniqueness constraint N/A — every allocation mints fresh values from the PIN pool, so uniqueness is guaranteed by generation. Before committing the reused pair, allocation verifies that neither customer_pin nor csp_pin is currently ALLOCATED to any other execution candidate anywhere in the registry. If either is in use elsewhere, fall back to a fresh allocation. This scenario is expected to be extremely rare in practice (see EDGE-4) but must be handled correctly. Protects the invariant that a PIN uniquely identifies one active ticket in the IVR at any moment. Prevents the theoretical case where a prior EC's PIN, since deallocated, has been reissued to a different ticket_id in the meantime.
Scope: RESTORE only The allocation code is ticket-type-agnostic — same flow for INSTALL, RESTORE, PICKUP, NBREC. The reuse lookup is guarded by ticket_type = 'RESTORE'. For all other ticket_types, allocation continues to mint fresh PINs as today (unchanged path). Verified by data: no other ticket_type exhibits multi-EC per ticket_id in the last 30 days. Restricting the change to RESTORE keeps the blast radius small and matches the observed problem exactly.
Row insertion pattern (audit trail) Each execution candidate gets its own pair of rows in ivr_pin_registry (one CUSTOMER, one CSP), with the PIN values that were freshly minted. Unchanged. A new pair of rows is still inserted per execution candidate — the PIN values are reused from the prior row, but the row itself is fresh (its own id, its own execution_candidate_id, its own allocated_at, its own visible flag, its own csp_id). One row per EC preserves the audit trail. Keeps the deallocation cascade unchanged (each EC still owns its own row and can be deallocated independently). Preserves the "one row per EC × party" invariant that downstream analytics rely on.
Concurrency guard N/A — no concurrent-EC handling exists for the same ticket_id. The allocation transaction takes a row-level advisory lock keyed on ticket_id before the lookup + insert, so two ECs arriving simultaneously for the same ticket_id serialise and both see the same (reused) PIN pair. First to insert wins; the second reads the just-inserted row and reuses the same PIN pair. The 8.4% churn population includes cases where two ECs land within seconds of each other. Without the lock, a race could cause both to allocate fresh (different) PINs and defeat the fix.
Feature flag / rollback N/A — behaviour is baked in. The reuse behaviour is gated by a Remote Config flag (e.g. ivr.pin.reuse_within_ticket_id.enabled). Default true post-release. Setting to false restores today's behaviour (fresh per EC) immediately, no service restart. Standard rollback lever. If an unexpected issue emerges post-deploy, the flag flips off and behaviour reverts to the current baseline without a code deploy.
Observability No specific metric distinguishes fresh vs reused PIN allocations. Two counters emitted at allocation time: ivr.pin.allocated.fresh (new PIN pair minted) and ivr.pin.allocated.reused (existing pair reused from prior EC on same ticket_id). Includes ticket_type dimension for slicing. Post-deploy verification: reused should account for ~8% of RESTORE allocations if the observed multi-EC rate holds. If the ratio drifts significantly the flag can be assessed.

Part B

How we will verify

Every rule above must be observable end-to-end. Each acceptance block ties back to an A5 row. Cover the happy path first, then the edges that would silently break it.

B5. Acceptance criteria HOW

What is expected: Given / When / Then blocks tied to concrete verification points. Include the negative cases: any row where the new logic doesn't fire, and any row where reuse must fall back to fresh allocation.

Business logic — happy path

LOGIC-1
Second RESTORE execution candidate for an existing ticket_id reuses the prior PIN
A customer's first RESTORE execution candidate closed 10 minutes ago; upstream creates a second EC for the same ticket_id.
Given
a RESTORE ticket_id T already has one row pair in ivr_pin_registry (customer_pin P_c, csp_pin P_s), both currently DEALLOCATED,
And
PINs P_c and P_s are not currently ALLOCATED to any other execution_candidate,
When
a new execution candidate EC2 arrives for the same ticket_id T (ticket_type RESTORE),
Then
allocation inserts a new pair of rows for EC2 with customer_pin = P_c and csp_pin = P_s,
And
both new rows are set to pin_status = ALLOCATED with fresh allocated_at and deallocated_at = NULL,
And
the counter ivr.pin.allocated.reused{ticket_type=RESTORE} increments by 1.
Verify:
  • DB — SELECT pin FROM ivr_pin_registry WHERE execution_candidate_id = 'EC2' AND type = 'CUSTOMER' returns P_c.
  • DB — SELECT pin FROM ivr_pin_registry WHERE execution_candidate_id = 'EC2' AND type = 'CSP' returns P_s.
  • IVR call — a caller dialling the masked number and entering P_c reaches Leg 2 to the CSP; Exotel row has Leg2Status = completed or no-answer (i.e., the bridge was attempted).
  • Metric — ivr.pin.allocated.reused emits a datapoint for this allocation.
LOGIC-2
First RESTORE execution candidate for a new ticket_id allocates fresh
Upstream creates the very first RESTORE EC for a brand-new ticket_id — no prior rows exist.
Given
a RESTORE ticket_id T has zero rows in ivr_pin_registry,
When
a new execution candidate EC1 arrives for ticket_id T,
Then
allocation mints a fresh (customer_pin, csp_pin) pair from the PIN pool,
And
inserts the pair of rows in ivr_pin_registry tagged to EC1, pin_status = ALLOCATED,
And
the counter ivr.pin.allocated.fresh{ticket_type=RESTORE} increments by 1.
Verify:
  • DB — the inserted PINs are not equal to any deallocated PIN for a different ticket_id (i.e., they came from the fresh pool).
  • Metric — ivr.pin.allocated.fresh emits; ivr.pin.allocated.reused does not.
LOGIC-3
Non-RESTORE execution candidates continue to allocate fresh (unchanged path)
INSTALL, PICKUP and NBREC execution candidates do not carry a ticket_id. The reuse lookup has no key to fire on, so allocation runs the existing fresh-mint path exactly as today.
Given
an execution candidate arrives with ticket_type IN (INSTALL, PICKUP, NBREC),
When
allocation runs,
Then
the ticket_id lookup returns nothing (the field is absent on non-RESTORE ECs),
And
a fresh PIN pair is minted from the pool as today,
And
the counter ivr.pin.allocated.fresh increments; ivr.pin.allocated.reused does not.
Verify:
  • Unit test — pass an INSTALL / PICKUP / NBREC EC; assert fresh PINs are minted and the reuse branch is not entered.
  • Metric — ivr.pin.allocated.reused emissions on non-RESTORE remain zero over the observation window.
LOGIC-4
Caller with a cached PIN from the closed prior EC bridges successfully after reuse
End-to-end: same customer / same ticket_id, EC1 closed, EC2 created via reuse. Customer or CSP dials the masked number and enters the PIN they had from EC1's SMS / chat.
Given
LOGIC-1 has fired (EC2 has been allocated using the reused PIN pair from EC1),
When
a caller dials the masked IVR number and enters P_c (the customer PIN from the closed EC1),
Then
the IVR identifies the ticket (via the now-ALLOCATED row on EC2 carrying the same P_c),
And
routes Leg 2 to the counterparty of EC2 (either the customer or CSP number on the EC2 rows),
And
Exotel records Leg1Status = completed and Leg2Status ∈ (completed, no-answer, canceled) — i.e., the bridge was attempted rather than the caller being trapped at the PIN prompt.
Verify:
  • Exotel CDR shows a to_number populated to the counterparty's mobile (not equal to the masked DID).
  • ivr.user_connection_call_logs row has to_number non-null, call_status ∈ (CONNECTED, MISSED_CALL, CANCELLED, REJECTED), i.e., not UNKNOWN.
