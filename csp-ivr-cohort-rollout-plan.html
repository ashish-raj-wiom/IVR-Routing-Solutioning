CSP IVR Service — Cohort-Based Rollout Plan

Roll out IVR 2.0 (masked-number bridging) on an opt-in cohort of CSPs instead of all-or-nothing. The IVR service owns an allow-list of enrolled CSPs and, on every call-CTA fetch, returns either a masked DID + PIN (when the CSP is enrolled) or the other party's actual mobile number (when not). Apps stay neutral — they just dial what they're given.

Audience: Engineering (csp-execution-platform, App teams) · Ops · Design Type: PM rollout-plan spec
Companion artefact: Base Product Solution Spec (v1.0). This document layers a phased rollout strategy on top of that spec; it does not modify the core IVR behaviour.

Quick Check

7-line summary. Reflects the body below.
What problem?
An all-CSP rollout of IVR 2.0 is too risky — we need a controlled cohort first to learn before expanding. Today's app-side kill switches are global ON/OFF; they cannot scope behaviour to specific CSPs.
Primary owner?
IVR service team (csp-execution-platform). Allow-list lives entirely inside the IVR service.
Migration needed?
No. App kill switches remain ON. No backfill of historical tickets. PIN allocation continues for every ticket as today.
App release needed?
Yes — minor. Apps add a one-branch handler on the existing call-CTA response (read callType: dial masked DID + PIN, or dial actual mobile).
Money flow change?
No.
PII processed?
Yes — same classes as today (CSP / customer mobiles). No new class.
Rollback latency?
≤ 30 seconds. Allow-list is in-memory cached with 30s TTL; removing a CSP propagates to all IVR instances within one cache cycle.

A2. Context & Problem Statement WHAT

What is expected: Why a cohort rollout is needed; what today's kill switch can and can't do; cost of skipping cohort phase.
QuestionAnswer
What is the current state?The base IVR 2.0 spec is built and partially live on prod. Both the CSP App and Customer App have a binary "IVR kill switch": when ON, the app calls the IVR service to fetch the masked-number routing target; when OFF, the app dials the other party's actual mobile directly. The kill switch is global — it affects every user simultaneously.
What can't the kill switch do?Scope behaviour to a subset. Either everyone gets masking or nobody does. Day-1 mass enablement carries every regression risk to every user at once, with no incremental learning.
Why is a cohort rollout needed?The IVR end-to-end flow involves: Exotel webhook timing, App-Bazaar Switch Case wiring, PIN allocation correctness, PIN-fetch endpoint correctness, Customer Service deserialization, sim_inventory recognition, and CleverTap notification path. Bugs in any of these silently break customer ↔ CSP communication. Recent prod incidents (CustomerClient deserialization bug, P74 PIN deallocation leak) confirm that hidden defects only surface once real traffic hits the system. We need a manageable blast radius to identify and fix these as they emerge.
What does this cohort plan add?A per-CSP enrolment list inside the IVR service that decides — on every call-CTA fetch — whether to return the masked-bridge response (PIN + masked DID) or fall back to returning the other party's actual mobile. Apps stay agnostic; they just dial whatever the IVR returns.
What happens if we skip this and just turn on the kill switch for everyone?Any defect would manifest as failed customer ↔ CSP calls across the entire base simultaneously. Reputational and operational cost of a full-base regression is materially higher than the engineering cost of building the cohort gate (~2 days of engineering work).
Governing principle"Crawl, walk, run" — prove correctness at small scale before exposing all users. The kill switch alone is insufficient because rolling back wholesale loses all the partial signal we've gained.

A3. Objective & Definition of Success WHAT

FieldValue
Core objectiveRoll IVR 2.0 to all CSPs with high confidence by progressing through size-bounded cohorts, learning from each cohort, and only expanding when metrics + qualitative signal both clear.
Definition of success (qualitative)Every CSP in the enrolled cohort experiences working masked calling in both directions. CSPs outside the cohort continue to call the other party directly, unchanged. Issues discovered in a cohort are fixed before expanding to the next cohort.
Quantitative success bars (per cohort)Bridge rate ≥ 85% of v2 calls (i.e., to_number set in user_connection_call_logs); Connect rate ≥ 30% of v2 calls; PIN-fetch error rate < 1% of calls; zero "masked number was actual number" incidents (privacy leakage).
Guardrail 1No CSP outside the enrolled cohort sees any change in behaviour. Their tickets continue to expose the other party's mobile via the existing call-CTA contract.
Guardrail 2A CSP can be removed from the cohort within ≤ 30 seconds (one cache cycle). No code change or service restart.
Guardrail 3Privacy invariant from the base spec is preserved: a real mobile number is never exposed to the counterparty for an enrolled CSP's tickets. Cohort gating does not weaken this contract; it only controls who is in the masking regime.
Rollback triggerAny of: (a) bridge rate drops below 70% across the cohort sustained over 24h; (b) any verified privacy leak (real number returned to counterparty when it shouldn't be); (c) a new bug class that affects ≥ 5 distinct CSPs in the cohort.

A4. Rollout Principles WHAT

What is expected: The four cornerstone decisions that govern this rollout.
DecisionChoiceWhy
Where does the allow-list live?IVR service (not in apps, not in TAS, not in any other service).Apps stay simple. Other services don't need to know. Single source of truth. Hot-reloadable.

A6. Business Logic & Invariants WHAT

IDInvariant
INV-ROLL-01The IVR service is the sole owner of the allow-list. Apps, TAS, and other services MUST NOT cache enrolment state independently.
INV-ROLL-02Enrolment is a CSP-level attribute. If CSP X is enrolled, every ticket whose CSP-side row in pin_registry has user_id = X is in the masking regime.
INV-ROLL-03Every call-CTA endpoint response includes a callType field with exactly one of two values: MASKED or DIRECT. No third value, no nulls.
INV-ROLL-04For callType = DIRECT, the IVR returns the other party's actual mobile sourced from pin_registry (the row that was allocated by TAS at ticket creation). It does not call any external lookup at CTA time.
INV-ROLL-05PIN allocation (POST /allocate) is uniform across all CSPs — enrolled or not. pin_registry remains a complete record of every Install / Restore / NBREC ticket.
INV-ROLL-06Cohort changes propagate to all IVR instances within ≤ 30 seconds. This is the rollback SLA.
INV-ROLL-07The base IVR's privacy invariants (no real mobile exposed in a masked bridge; PIN-binding to ticket) are unaffected. Cohort gating is an additional layer on top, not a relaxation.

A7. Edge Cases & Decisions WHAT

Edge caseDecision
CSP is removed from cohort while their tickets have active PINs.The PIN rows stay in pin_registry (untouched). New call-CTA fetches return DIRECT. The previously-issued masked DID + PIN combination still works if dialled (Path 2 by-FROM lookup still hits), so any in-flight ringing call completes. Net: no broken calls during transition.
CSP is added to cohort while they have in-flight tickets.Per A4 — no backfill. New call-CTA fetches on those tickets now return MASKED (the PIN already exists from TAS' standing /allocate calls). User experience flips smoothly on the next CTA tap.
Migrated ticket (pre-IVR-2.0 launch) for an enrolled CSP — no pin_registry row exists.The IVR has no PIN to return. Fallback: return DIRECT with the other party's actual mobile sourced from app's local task data. Requires a small additional path in app: if IVR returns 404 / not-found for an enrolled-CSP ticket, the app uses its local mobile. Flagged for B-spec resolution.
Customer of an enrolled CSP receives a call from non-helpline number (legacy direct call from CSP).Out of scope. The cohort gate only affects what IVR returns on app CTA. Any other channel (WhatsApp, personal SIM, etc.) is unchanged.
Customer has tickets across two CSPs — one enrolled, one not.Per ticket: each call CTA fetch is keyed on the ticket's CSP. The customer may experience masked calling for one ticket and direct calling for another. This is acceptable and follows from CSP-level granularity.
CSP App version doesn't yet support polymorphic callType response.The endpoint stays backward compatible. Old app reads pin field as before — IVR continues to set pin in MASKED responses. For DIRECT responses, pin is absent / null; old app would interpret as "no PIN available", which is the safe failure mode (matches today's kill-switch-off behaviour). Recommended path: ship app update before / alongside enrolling that CSP's users.
An enrolled CSP's customer dials the masked helpline but their CSP gets de-enrolled before they hang up.The mid-call bridge continues unaffected (Exotel session already established). Next call attempt would route per the new state.
TAS calls /allocate for a non-enrolled CSP's ticket.IVR allocates as usual. Per A4 / INV-ROLL-05.

B1. Data Model — Allow-list HOW

What is expected: The table that stores the enrolment list, plus an audit table for change tracking.

B1.1 Primary table

CREATE TABLE ivr.ivr_csp_enrolment (
  csp_id           VARCHAR(16) PRIMARY KEY,
  enrolled_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  enrolled_by      VARCHAR(64),                        -- admin user / system
  notes            TEXT,
  active           BOOLEAN      NOT NULL DEFAULT TRUE,
  deactivated_at   TIMESTAMPTZ
);

CREATE INDEX idx_ivr_csp_enrolment_active
  ON ivr.ivr_csp_enrolment (active)
  WHERE active = TRUE;

B1.2 Audit table

CREATE TABLE ivr.ivr_csp_enrolment_audit (
  id          BIGSERIAL    PRIMARY KEY,
  csp_id      VARCHAR(16)  NOT NULL,
  action      VARCHAR(16)  NOT NULL,  -- ENROLLED | DEACTIVATED | REACTIVATED
  actor       VARCHAR(64),
  at          TIMESTAMPTZ  DEFAULT NOW(),
  notes       TEXT
);

CREATE INDEX idx_ivr_csp_enrolment_audit_csp_at
  ON ivr.ivr_csp_enrolment_audit (csp_id, at DESC);

B1.3 Why soft-delete (active flag) instead of physical delete?

Removing a CSP from the cohort during rollback is a frequent operation. Soft-delete preserves historical context (when they were enrolled, who removed them, when), and re-enrolment becomes a single UPDATE instead of a fresh INSERT — losing audit chain. The active = TRUE partial index keeps reads cheap.

B2. API Contract — Polymorphic Response HOW

What is expected: The shape of the call-CTA endpoint's response in both the MASKED and DIRECT cases.

B2.1 Affected endpoints

EndpointCallerReturns the mobile of
POST /api/v1/ivr/pin-registry/customer/pinCustomer AppThe CSP (counterparty)
POST /api/v1/ivr/pin-registry/csp/pinCSP App / Technician AppThe customer (counterparty)

B2.2 MASKED response (CSP is enrolled)

{
  "callType":  "MASKED",
  "pin":       "032841",
  "maskedDid": "08047284012"
}

App behaviour: dial maskedDid; on prompt, send pin as DTMF. This is today's masked-bridge flow.

B2.3 DIRECT response (CSP is NOT enrolled)

{
  "callType":    "DIRECT",
  "phoneNumber": "9876543210"
}

App behaviour: dial phoneNumber directly. Equivalent to today's "kill switch off" behaviour.

B2.4 Where the actual mobile comes from for DIRECT

EndpointSource of phoneNumber
customer/pinpin_registry row where type = CUSTOMER AND ticket matches → number field = CSP's mobile
csp/pinpin_registry row where type = CSP AND execution_candidate_id matches → number field = customer's mobile

Both endpoints already read pin_registry to fetch the PIN; reading the number column from the same row is zero extra IO. No external lookup needed.

B2.5 Backward compatibility

  • The pin field in responses stays. Old apps continue to read it and behave correctly for the MASKED case.
  • For DIRECT responses, pin is absent. Old apps interpreting "no PIN" as "fall back to local mobile" is the safe failure mode — matches the legacy kill-switch-off branch.
  • The new callType and phoneNumber fields are additive; old apps ignore them harmlessly.

B2.6 Decision pseudocode (IVR-side)

function handleCallCtaFetch(ticketContext) {
  cspId = resolveCspId(ticketContext);              // from pin_registry CSP-side row
  if (enrolmentCache.isEnrolled(cspId)) {
    pin       = fetchPin(ticketContext);
    maskedDid = config.maskedDid;                   // "08047284012"
    return { callType: "MASKED", pin, maskedDid };
  } else {
    phoneNumber = fetchCounterpartyMobile(ticketContext);
    return { callType: "DIRECT", phoneNumber };
  }
}

B3.1 Bulk onboarding

For Phase 1 → Phase 3 expansions, the cohort grows in chunks of 5 / 50 / 500 CSPs. Two acceptable mechanisms:

  • Bulk SQL — direct INSERT with a single batch query, run via the DB admin console. Fast, low ceremony, but no per-row audit.
  • Scripted API calls — Ops script loops the POST endpoint, one CSP at a time. Slower but writes proper audit rows.

Recommendation: scripted API for any cohort growth that's part of the formal rollout phases. Direct SQL only for emergency rollback (mass remove).

B5. Inbound Helpline Behaviour HOW

No change vs the base spec. The Connect-applet API (POST /api/v1/connect-applet) does not consult the cohort allow-list. All inbound calls to the masked DID (08047284012) flow through Path 1 (Redis Table 1) and Path 2 (pin_registry by-FROM) as today, regardless of the originating CSP's enrolment state.

Rationale: the helpline is shared infrastructure. Customers / CSPs who reach it have done so via legitimate means (in-app CTA at some prior point, or callback from an Exotel-recorded missed call). Cohort filtering at the inbound layer would create silent drops with no clean user-facing recovery path — which is the exact failure mode the base IVR spec was built to eliminate.

B6. PIN Allocation Behaviour HOW

No change. TAS continues to call POST /api/v1/ivr/pin-registry/allocate for every Install / Restore / NBREC ticket at candidate creation, regardless of CSP enrolment state. The allow-list does not gate /allocate.

ImplicationDetail
PIN pool consumption~few hundred PINs per day allocated to tickets that will never use them (non-enrolled CSPs). Pool size is 1M; negligible drain. PIN cooldown / recycle (POST /recycle) returns these to the pool naturally.
pin_registry contentsContinues to hold a complete record of every ticket across all CSPs. Useful for observability — we can measure the size of the would-be cohort by inspecting pin_registry.
If a non-enrolled CSP gets enrolled mid-flightTheir existing tickets already have PINs allocated. Enrolment flips them to MASKED on the next call-CTA fetch without any additional allocation step.
TAS coordination required?None. TAS is enrolment-agnostic.

B8.1 Selection criteria for Pilot & Phase 2 cohorts

  • Active ticket flow in at least 2 of {Install, Restore, NBREC} — to exercise all PIN-allocation paths.
  • At least 2 distinct zones represented — to catch any region-specific issues (telco-routing, masked-DID coverage).

B11. Out of Scope HOW

  • Legacy customer IVR DID (01141168600) — continues to operate in parallel. Not affected by this rollout.
  • Legacy partner initiateCall API (service=PARTNER) — continues to serve older CSP app versions for outbound calls. Not gated by enrolment.

callTypeThe discriminator field in the call-CTA response that tells the app which branch to take. Exactly two values: MASKED or DIRECT.
Kill switchThe pre-existing app-side boolean that controls whether the app uses IVR routing at all. Per this plan, stays ON permanently and is effectively unused.
