CSP IVR Service — Cohort-Based Rollout Plan

Roll out IVR 2.0 (masked-number bridging) on a cohort of CSPs instead of all-or-nothing. The IVR service maintains a list of enrolled CSPs. When the app fetches the number to dial at the moment the user taps the call CTA, the IVR returns the masked number (for cohort CSPs) or the other party's actual mobile (for everyone else) — in the same response field the app already reads today. No app-side change is required.

Audience: Engineering (csp-execution-platform, App teams) · Ops · Design Type: PM rollout-plan spec
Companion artefact: Base Product Solution Spec (v1.0). This document layers a phased rollout strategy on top of that spec; it does not modify the core IVR behaviour.

A2. Context & Problem Statement WHAT

What is expected: Why a cohort rollout is needed; what today's kill switch can and can't do; cost of skipping cohort phase.
QuestionAnswer
What is the current state?The base IVR 2.0 spec is built and partially live on prod. Both the CSP App and Customer App have a binary "IVR kill switch": when ON, the app calls the IVR service to fetch the masked-number routing target; when OFF, the app dials the other party's actual mobile directly. The kill switch is global — it affects every user simultaneously.
What can't the kill switch do?Scope behaviour to a subset. Either everyone gets masking or nobody does. Day-1 mass enablement carries every regression risk to every user at once, with no incremental learning.
Why is a cohort rollout needed?The IVR end-to-end flow involves: Exotel webhook timing, App-Bazaar Switch Case wiring, PIN allocation correctness, PIN-fetch endpoint correctness, Customer Service deserialization, sim_inventory recognition, and CleverTap notification path. Bugs in any of these silently break customer ↔ CSP communication. Recent prod incidents (CustomerClient deserialization bug, P74 PIN deallocation leak) confirm that hidden defects only surface once real traffic hits the system. We need a manageable blast radius to identify and fix these as they emerge.
What does this cohort plan add?A per-CSP enrolment list inside the IVR service that decides — on the number-fetch call at CTA time — whether to return the masked DID (cohort path) or the other party's actual mobile (non-cohort path). Apps stay agnostic; they just dial whatever the IVR returns.
Relationship to PIN?PINs are already being created for every Install / Restore / Pickup ticket today, and the apps already pre-fetch them. This rollout doesn't change any of that. The PIN simply doesn't get exercised for non-cohort tickets, because the call doesn't go through the masked bridge.
What happens if we skip this and just turn on the kill switch for everyone?Any defect would manifest as failed customer ↔ CSP calls across the entire base simultaneously. Reputational and operational cost of a full-base regression is materially higher than the engineering cost of building the cohort gate (~2 days of engineering work).
Governing principle"Crawl, walk, run" — prove correctness at small scale before exposing all users. The kill switch alone is insufficient because rolling back wholesale loses all the partial signal we've gained.

FieldValue

A4. Rollout Principles WHAT

What is expected: The four cornerstone decisions that govern this rollout.

The app's existing render logic naturally skips the PIN block when there is nothing to show — no app code change required.Symmetry with the masking decision. If the call won't use the PIN, neither party should be looking at it.

Going forward from the moment the CSP joins the cohort, every call CTA on every one of their tickets (including ones created earlier) will return the masked number. No retroactive change to the tickets themselves.Simplest. The cohort decision is made fresh on every call CTA, so adding a CSP is enough — nothing has to be re-stamped on existing tickets.

Part B

HOW — Detailing

Engineering-facing detail. Subject to revision as build progresses; the WHAT decisions above are the stable contract.

B1. What the IVR Service Does HOW

What is expected: The business-level behaviour the IVR service needs to support to enable cohort-based rollout.

B1.1 The cohort list

The IVR service holds a list of CSPs that are currently in the masking regime. The list is maintained by the IVR team; nobody else has direct access. A CSP can be added or removed at any time, and the change takes effect across the IVR service within seconds — no app release, no service restart, no coordination with other teams.

B1.2 The single gate: a visibility flag on the PIN row

For every Install / Restore / Pickup ticket, a row is created in pin_registry as today. The IVR adds one new column on that row — a visible flag — and sets it based on the ticket's CSP:

  • CSP is in the cohort → visible = true.
  • CSP is not in the cohort → visible = false.

That single flag is the gate for everything visible to the user:

  • Call CTA — number to dial. When the app asks the IVR for the number, the IVR consults the flag. visible=true → return the masked number. visible=false → return the other party's actual mobile.
  • PIN-fetch endpoint. When the app pre-fetches the PIN for the ticket card, the IVR consults the flag. visible=true → return the PIN. visible=false → return "no PIN" (the app's existing render logic naturally hides the PIN block; no app change needed).
  • PIN-created event to CleverTap. The event that drives the PIN SMS and the PIN push notification is emitted only when visible=true. When the flag is OFF, no event reaches CleverTap, so no SMS and no push reach either party.

This is the only place the cohort decision is consulted. Everything else — PIN creation itself, inbound calls to the helpline number, allocation triggers from upstream services — continues to behave identically for cohort and non-cohort CSPs.

B1.3 Where the IVR gets the actual number for non-cohort CSPs

Both parties' mobile numbers are already known to the IVR at ticket creation time (the upstream service that creates the ticket also tells the IVR who the customer and CSP are). So when a non-cohort CSP's ticket triggers a number-fetch, the IVR can return the right "actual" number immediately, without calling any other service in the middle of the call CTA flow.

B1.4 Managing the cohort list

The IVR team needs to be able to: add a CSP to the cohort, remove a CSP from the cohort, and view the current list and recent changes. These operations are internal-only (no public surface) and happen at human-managed frequency (a few times a day during early rollout; less often later). Each change cascades to the visible flag on every active PIN row for that CSP — so flipping cohort membership is one operational step, not many.

B1.5 What is NOT changing in the IVR service

  • PIN creation logic for new tickets — a row still appears in pin_registry for every Install / Restore / Pickup, regardless of cohort state.
  • The PIN-fetch endpoint contract — same URL, same response shape; only the value of the PIN field changes (a PIN or null) based on the flag.
  • Inbound call routing on the helpline number (callers always reach a bridge as today).
  • The masked DID configuration, sim inventory.
  • Privacy guarantees: when a call does go through the masked bridge, no real mobile is exposed to the counterparty.

B2. Inbound Helpline Behaviour HOW

The IVR helpline number accepts calls from everyone, exactly as today. The cohort decision does not apply to inbound calls.

Reason: the helpline is shared infrastructure. Customers and CSPs who happen to dial it (from an old SMS, a saved contact, a missed-call callback) shouldn't be cut off mid-flow. Filtering at the helpline would create silent drops with no clear recovery path — the exact problem the base IVR was built to eliminate.

B4. App-Side Changes HOW

What is expected: Confirmation of which side of the system needs to change for this rollout.

No frontend release is required. Not one. Not for any phase, not for any cohort change. The Customer App, CSP App and Technician App stay on whatever version they're currently shipping. The IVR service is the sole locus of change.

This works because, for each of the four surfaces a user sees, the gating happens server-side before the app gets involved:

SurfaceWhy no app change is needed
Number to dial on Call CTAApp already calls the IVR for the number and dials whatever comes back. IVR returns masked or actual based on the visible flag. App is none the wiser.
PIN shown on the ticket cardApp already calls the IVR's PIN-fetch endpoint and renders the PIN if one comes back. For non-cohort tickets the endpoint returns no PIN, so the app's existing "render nothing if empty" branch fires.
PIN SMSSMS is fanned out by CleverTap on a PIN-created event. The IVR (the emitter) suppresses the event for non-cohort tickets — no event, no SMS. CleverTap config doesn't change. App doesn't change.
PIN push notification / in-app educationSame path as SMS — CleverTap-driven, gated at the event emitter. No change anywhere on the client.

No release coordination is needed with the mobile teams to roll out the cohort. The IVR team can add or remove CSPs from the cohort independently — and that single action propagates through all four surfaces automatically.

B5. Acceptance Criteria HOW

What is expected: Observable behaviours that must hold for the cohort rollout to be considered correct. Each scenario is testable by direct observation (placing a real call, looking at the dialler, checking the call log) — no API or DB inspection required.

B5.1 Outbound calls — cohort CSPs

AC-01 CSP user calls customer on a cohort CSP's ticket

Given the CSP is in the cohort,

When a user on that CSP taps the call CTA on any ticket card,

Then the call connects to the customer through the Wiom masked bridge,

And the customer's phone shows the Wiom helpline number — not the CSP user's mobile,

And a recording of the call is saved.

AC-02 Customer calls CSP on a cohort CSP's ticket

Given the customer's CSP is in the cohort,

When the customer taps the call CTA on the ticket in the Customer App,

Then the call connects to the CSP user through the Wiom masked bridge,

And the CSP user's phone shows the Wiom helpline number — not the customer's mobile,

And a recording of the call is saved.

B5.2 Outbound calls — non-cohort CSPs

AC-03 CSP user calls customer on a non-cohort CSP's ticket

Given the CSP is NOT in the cohort,

When a user on that CSP taps the call CTA on any ticket card,

Then the call goes through as a normal phone call to the customer's mobile,

And the customer's phone shows the CSP user's actual mobile (today's behaviour),

And no masked routing is involved.

AC-04 Customer calls CSP on a non-cohort CSP's ticket

Given the customer's CSP is NOT in the cohort,

When the customer taps the call CTA on the ticket in the Customer App,

Then the call goes through as a normal phone call to the CSP user's mobile,

And the CSP user's phone shows the customer's actual mobile (today's behaviour).

B5.3 Cohort membership changes

AC-05 CSP is added to the cohort mid-flight

Given a CSP is not in the cohort and has open tickets,

When the IVR team adds the CSP to the cohort,

Then within a few seconds, the next call CTA on any of their tickets routes through the masked bridge,

And no app release, app restart, or service restart is needed,

And existing open tickets automatically switch to masked routing without any backfill step.

AC-06 CSP is removed from the cohort (rollback)

Given a CSP is in the cohort,

When the IVR team removes the CSP from the cohort,

Then within a few seconds, the next call CTA on their tickets routes as a direct call,

And any call already connected through a masked bridge continues uninterrupted until the parties hang up,

And no app release, app restart, or service restart is needed.

B5.4 Inbound calls to the helpline

AC-07 Customer dials the Wiom helpline number directly

Given a customer dials the Wiom helpline number directly (e.g., from an old SMS or saved contact), regardless of whether their CSP is in the cohort,

When the call reaches the IVR,

Then the IVR bridges them to the right party as today,

And the call is not blocked, dropped, or sent to a dead-end based on cohort state.

B5.5 PIN behaviour

AC-08 PIN is created and pre-fetched regardless of cohort state

Given a new Install / Restore / Pickup ticket is created,

When the ticket loads on the relevant app,

Then a PIN is created in the background and the app pre-fetches it on the ticket card,

And this happens for cohort CSPs and non-cohort CSPs alike.

AC-09 PIN is used only when the call goes through the masked bridge

Given a ticket has a pre-fetched PIN on the app,

When the user taps the call CTA,

Then if the CSP is in the cohort, the PIN is sent on the call (during the masked bridge),

And if the CSP is not in the cohort, the PIN sits unused and no harm is done.

AC-09a PIN is not shown in either app for a non-cohort CSP's ticket

Given the ticket's CSP is NOT in the cohort,

When the customer opens the ticket in the Customer App, and when a CSP user opens the ticket in the CSP App,

Then the PIN block does not appear on either ticket card,

And the literal string PIN_NOT_AVAILABLE (or any placeholder) is not rendered anywhere on the card,

And no app release was needed to achieve this — the IVR's PIN-fetch endpoint returned no PIN and the apps' existing "hide if empty" logic took care of the rest.

AC-09b No PIN SMS or push notification is sent for a non-cohort CSP's ticket

Given the ticket's CSP is NOT in the cohort,

When the ticket is created and the PIN row appears in pin_registry with visible=false,

Then the PIN-created CleverTap event is not emitted,

And the customer does not receive the customer-PIN SMS,

And the CSP user does not receive the CSP-PIN SMS,

And neither party receives a PIN-related push notification or in-app education message for that ticket.

AC-09c All four user-facing surfaces light up together when a CSP joins the cohort

Given a CSP is added to the cohort,

When the visible flag on their active PIN rows flips to true,

Then the IVR's PIN-fetch endpoint starts returning the PIN for those tickets,

And the call CTA on those tickets starts returning the masked number,

And the PIN-created CleverTap event starts firing for newly created tickets of that CSP,

And the customer and CSP user start receiving the PIN SMS + push for those new tickets.

B5.6 Privacy

AC-10 No real mobile is exposed on a cohort call

Given a CSP is in the cohort,

When any call goes through their ticket via the masked bridge (either direction),

Then the customer's call log shows only the Wiom helpline number,

And the CSP user's call log shows only the Wiom helpline number,

And neither party's personal mobile is exposed to the other at any point.

B5.7 Repeat-tap consistency

AC-11 Consecutive call CTAs are consistent

Given a ticket card,

When the user taps the call CTA twice within a few seconds,

Then both attempts route the same way (both masked, or both direct),

And the cohort decision is consistent within that short window.

B5.8 App-side neutrality

AC-12 No frontend release is needed at any stage of the rollout

Given any version of the Customer App / CSP App / Technician App currently in the field,

When CSPs are added to or removed from the cohort, and when the cohort grows from Phase 1 through Phase 4,

Then none of these app versions need an update for the cohort change to take effect,

And the app's existing logic — ask the IVR for the number, ask the IVR for the PIN, render the PIN if returned, dial whatever number comes back — handles every combination of cohort and non-cohort tickets correctly,

And the same applies to the SMS / push notification surfaces, which are gated server-side via the CleverTap event emitter and require no client change.

A nightly check inspects a sample of cohort calls and confirms that the numbers exchanged between the two parties were the Wiom masked number, not their personal mobiles. Any case where a personal mobile shows up on a cohort call triggers an alert.

B9. Out of Scope HOW

  • Legacy customer IVR helpline — continues to operate in parallel. Not affected by this rollout.
  • Legacy CSP-app outbound calling path — older CSP app versions that use the legacy call-setup flow continue to work as today, irrespective of cohort state.
  • Customer-side cohort logic — there is no customer-level cohort list. A customer's experience is decided by whether the CSP on their ticket is in the cohort.
  • Notification gating — the SMS / push notifications for PIN delivery are unaffected. Customers and CSPs continue to receive them as today, regardless of cohort state. The PIN simply doesn't get used for non-cohort CSPs.
  • Migrated tickets that pre-date the IVR 2.0 launch and have no PIN in the system — flagged as OQ-1; resolved before Phase 1 kickoff.
  • Admin UI for managing the cohort — not built in this phase. The IVR team makes changes directly until volume warrants tooling.

Glossary

TermDefinition
Cohort / Cohort listThe set of CSPs whose tickets are currently in the masked-routing regime. Maintained inside the IVR service.
Cohort CSPA CSP currently present in the cohort list.
Masked pathWhat happens on a cohort CSP's ticket: the app dials the Wiom masked number, and the call goes through the IVR routing layer that bridges the two parties without exposing either personal number.
Direct pathWhat happens on a non-cohort CSP's ticket: the app dials the other party's actual mobile directly. The IVR is not involved.
Number-fetch (at call CTA tap)The moment the app asks the IVR for a number to dial. This is the single point where the IVR consults the cohort list.
PIN pre-fetch (when the ticket loads)An earlier, separate step where the app retrieves the PIN for the ticket and stores it locally. Unchanged by this rollout. The PIN is used only when the call goes through the masked path; for the direct path it sits unused.
Kill switchThe pre-existing app-side boolean that controls whether the app uses IVR routing at all. Per this plan, stays ON permanently and is effectively unused.
Cache cycle30-second refresh interval of the in-memory enrolment cache. Equal to the rollback propagation SLA.
