In-app Call CTA

UC 01 CSP user taps Call CTA in the CSP App (registered SIM)
Path 1 ✓ Live

The happy path. A CSP user opens a ticket in the CSP App and taps the Call CTA to reach the customer. The dialler opens with the Wiom masked number pre-filled. The user dials, and the call is bridged seamlessly via the active mapping (Table 1). The customer's phone shows the Wiom helpline number, never the CSP user's mobile.

  1. CSP user (in CSP App)
    Opens a Restore / Install / Pickup ticket card.
  2. CSP user
    Taps the Call CTA.
  3. CSP App ↔ IVR
    App asks the IVR for the number to dial; IVR creates a short-TTL active mapping and returns the masked number.
  4. CSP user
    Dialler opens with the masked number; user taps dial.
  5. IVR
    Bridges to the customer — Table 1 cache hit, no PIN prompt.
  6. Customer's phone
    Rings showing the Wiom helpline number; customer picks up; call connects.
Dependent features (all required)
  • Exotel App Bazaar Flow ✓
  • API 1 (Table 1 fetch) ✓
  • API 4 / Webhook (call logging) ✓
  • CSP App integrations ✓
  • Remote Config kill switch ✓

Dialer-initiated callbacks — recognised caller

UC 03 CSP dials back the masked number from their call log — single active ticket
Path 2 ✓ Live

A CSP user previously called a customer via the in-app CTA. Later they want to re-call — they tap the Wiom helpline entry in their phone's call log. Table 1's TTL has expired so the cached mapping is gone. The IVR recognises their FROM (registered SIM or sim_inventory) and finds exactly one active ticket — bridges directly.

  1. CSP user
    Opens their phone's call log; finds the Wiom helpline entry; taps dial.
  2. IVR (API 1)
    Looks up FROM in Table 1 → cache miss. Falls back to PIN registry by FROM.
  3. IVR
    Identification chain — first hit: FROM matches a row in sim_inventory → returns the user_id. Finds exactly 1 active ticket for that CSP → directly returns the customer's mobile as the bridge target.
  4. IVR
    Bridges to the customer — no PIN prompt needed.
  5. Customer's phone
    Rings; picks up; call connects.
Dependent features
  • API 1 ✓ · API 2 (user identification) ✓ · API 4 webhook ✓
  • "All Recorded Voices" (covers fallback if no active ticket) ✓
UC 04 CSP dials back from call log — multiple active tickets
Path 3 ✓ Live

Same as UC 03 but the CSP has 2 or more active tickets — the IVR can't tell which customer they want to reach. It asks for the 6-digit PIN. The CSP reads the PIN from the relevant ticket card in the CSP App and enters it on the dialler keypad. The PIN identifies the ticket and the bridge fires.

  1. CSP user
    Taps the Wiom helpline entry in their call log.
  2. IVR
    FROM recognised but 2+ active tickets → can't auto-resolve.
  3. IVR (audio prompt)
    Asks the caller to enter the 6-digit PIN.
    ▶ Audio: "Ask for PIN"
    Played when IVR needs the caller to enter their PIN to disambiguate the ticket.
  4. CSP user
    Opens the relevant ticket in the CSP App, reads the PIN from the card, enters it on the dialler keypad.
  5. IVR (API 3)
    Looks up the PIN in Table 2; finds the customer mobile.
  6. IVR
    Bridges to the customer.
▶ Failure modes — wrong PIN / no PIN entered / 3 wrong attempts
If the user enters the wrong PIN, doesn't enter anything, or burns through three retries, the IVR plays one of these messages and ends the call.
Dependent features
  • API 1 ✓ · API 2 ✓ · API 3 (PIN lookup) ✓ · API 4 ✓
  • PIN visible on CSP App ticket card ✓
  • All Recorded Voices ✓

Unknown caller — unregistered SIM

UC 11 Customer dials from an unregistered SIM (relative's phone, secondary SIM)
Path 4 ✓ Live

A customer borrows a relative's phone (their own is unreachable). The masked number is on the SMS they received at ticket creation. They dial it. The IVR doesn't recognise the FROM, asks for the PIN; they read it from the same SMS and enter it.

  1. Customer
    From an unregistered SIM, dials the Wiom helpline number that was sent in their SMS.

  3. IVR
    Plays the PIN prompt.
    ▶ Audio: "Ask for PIN"
  4. Customer
    Reads the PIN from the SMS on their own phone; enters it on the borrowed phone's keypad.
  5. IVR (API 3)
    Looks up PIN → finds the CSP mobile.
  6. IVR
    Bridges to the CSP.
▶ Failure modes

    ▶ Audio: "Ask for PIN"

UC 13 CSP forwards the masked number to a colleague — colleague dials
Path 4 ⚠ Partial

A CSP user can't take the call (signal, busy, away). They forward the masked number + PIN to a colleague (via WhatsApp / SMS — typically a screenshot of the ticket card). The colleague dials and enters the PIN.

  1. CSP user

  2. Colleague
    Receives the forward; dials the masked number from their own phone.
  3. IVR
    Table 1 miss. Identification chain runs and all three steps miss (colleague's phone is in none of sim_inventory, Customer API, or Booking API). Caller is unknown.
  4. IVR
    Plays the PIN prompt.
    ▶ Audio: "Ask for PIN"
  5. Colleague
    Reads the PIN from the forwarded message; enters it on the keypad.
  6. IVR
    Bridges to the customer.
Dependent features
  • API 1 ✓ · API 2 ✓ · API 3 ✓ · API 4 ✓ · Recorded voices ✓
  • PIN visible on CSP App ✓ (CSP can screenshot or copy)
  • PIN SMS to CSP — Blocked. The intended share mechanism (forward the SMS) doesn't work today. The CSP can still screenshot the app ticket card and forward that — workable but lossier.

Edge-case audio (no active ticket on dial-back)

When a previously-engaged customer or CSP dials the helpline back but has no active ticket (e.g., ticket already closed), the IVR plays a dedicated message and ends the call. This is a graceful dead-end, not a use case branch on its own — but the audio is part of the contract.

No active ticket — Customer side
Played when a customer dials back but has no open ticket.
No active ticket — CSP / Partner side
Played when a CSP user dials back but has no open ticket.
Call not picked
Played when the dialled party (customer or CSP) doesn't pick up before the timeout — call ends.

The 13 use cases collapse into four distinct routing paths. Each path has its own logic; below is one flowchart per path showing exactly what the IVR does on the call.

Master flow — how the IVR routes any incoming call

Applies to all 13 use cases. Branches into Paths 1–4 based on what's known about the caller.

When a call arrives at the IVR (via the masked number), the very first thing it does is a Table 1 cache lookup. From there, the four paths branch out.

flowchart TD
    Call([Call arrives at masked number]) --> T1{Table 1 active mapping}
    T1 -->|HIT| P1[Path 1 In-app CTA happy path - bridge directly]
    T1 -->|MISS| Chain[Identification chain runs]
    Chain -->|Recognised| Tick{Active ticket count}
    Tick -->|Exactly 1| P2[Path 2 Direct bridge no PIN]
    Tick -->|Two or more| P3[Path 3 PIN prompt to disambiguate]
    Tick -->|Zero| Dead[Play no-active-ticket and end call]
    Chain -->|All 3 lookups miss| P4[Path 4 PIN prompt to authenticate]
    P1 --> Done([Call connects])
    P2 --> Done
    P3 -->|Correct PIN| Done
    P4 -->|Correct PIN| Done
    P3 -->|3 wrong| EndCall[Play limit-reached and end call]
    P4 -->|3 wrong| EndCall

Path 1 — In-app CTA happy path

Covers: UC 01 (CSP from CSP App) · UC 02 (Customer from Customer App)

The user taps the in-app Call CTA on their ticket. The app pre-asks the IVR for the number to dial. The IVR writes a short-TTL mapping into Table 1 and returns the masked number. The user dials it; the IVR recognises the mapping and bridges instantly.

flowchart LR
    A([User taps Call CTA in app]) --> B[App asks IVR for the number to dial]
    B --> C[IVR creates Table 1 mapping]
    C --> D[IVR returns the masked number]
    D --> E[App opens dialer with masked number]
    E --> F[User taps dial]
    F --> G[Call lands at IVR via masked number]
    G --> H{Table 1 still has mapping}
    H -->|YES TTL ok| I[Bridge directly to counterparty]
    H -->|NO TTL expired| Fallback[Falls to Path 2 3 or 4]
    I --> J([Call connects])

Path 2 — Recognised caller, single active ticket

Covers: UC 03 · UC 05 · UC 07 · UC 09 — every "dial back from call log, exactly one open ticket" scenario.

Table 1 has expired. The IVR runs the identification chain to figure out who's calling. The first step that hits (sim_inventory, Customer API, or Booking API) gives the IVR enough to look up active tickets for the caller. If there's exactly one — bridge directly, no PIN needed.

flowchart TD
    A([Caller dials masked number from call log]) --> B[Call lands at IVR]
    B --> C{Table 1 lookup}
    C -->|Miss| D[Identification chain starts]
    D --> S1{sim_inventory FROM matches}
    S1 -->|YES returns user_id| Find[Find active tickets for this user]
    S1 -->|No| S2{Customer API FROM matches}
    S2 -->|YES returns customer_id| Find
    S2 -->|No| S3{Booking API FROM matches}
    S3 -->|YES returns account_id| Find
    S3 -->|No| P4[Falls to Path 4]
    Find --> Count{Active ticket count}
    Count -->|Exactly 1| Bridge[Bridge to the one counterparty]
    Count -->|Zero| Dead[Play no-active-ticket and end call]
    Count -->|Two or more| P3[Falls to Path 3]
    Bridge --> Done([Call connects])

Path 3 — Recognised caller, multiple active tickets → PIN

Covers: UC 04 · UC 06 · UC 08 · UC 10 — caller is identified but they have 2+ open tickets, so the IVR can't tell which counterparty they want.

The IVR plays the "ask for PIN" audio. The caller reads the PIN from their ticket (in-app card for CSP, SMS or in-app for customer) and enters it. The PIN itself identifies the ticket; the IVR looks up the counterparty's mobile and bridges. Three wrong attempts → dead-end.

flowchart TD
    Start([Caller dials masked number]) --> Pre[Identification chain hits but 2+ active tickets found]
    Pre --> A[IVR plays Ask-for-PIN audio]
    A --> B[Caller enters 6-digit PIN from ticket card or SMS]
    B --> C{PIN valid and maps to an active ticket}
    C -->|YES| D[API 3 returns counterparty mobile]
    D --> E[Bridge to counterparty]
    E --> Done([Call connects])
    C -->|Wrong PIN| F[Play Wrong-PIN audio]
    F --> G{Attempt count}
    G -->|Under 3| A
    G -->|3rd wrong| H[Play Limit-reached and end call]
    C -->|No PIN entered| I[Play No-PIN-entered and end call]

Path 4 — Unknown caller → PIN

Covers: UC 11 (customer from unregistered SIM) · UC 12 (CSP from unregistered SIM) · UC 13 (colleague forwarding).

The caller's mobile fails all three identification lookups — IVR doesn't know who they are. The PIN serves double duty here: it both authenticates the caller (they wouldn't have it unless someone authorised gave it to them) and identifies the ticket they want.
