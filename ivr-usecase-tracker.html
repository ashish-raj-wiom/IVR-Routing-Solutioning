In-app Call CTA

UC 01 CSP user taps Call CTA in the CSP App (registered SIM)
Path 1 ✓ Live

A CSP user opens a ticket in the CSP App and taps the Call CTA to reach the customer. The dialer opens with the Wiom IVR Masked number pre-filled. The user dials, and the call is bridged seamlessly — no PIN prompt, no waiting. The customer's phone shows the Wiom IVR Masked number, never the CSP user's personal mobile.

How it works — business flow

What the user does and sees

  1. CSP user opens a Restore / Install / Pickup ticket card in the CSP App.
  2. Taps the Call CTA.
  3. Phone dialer opens with the Wiom IVR Masked number pre-filled.
  4. Taps dial.
  5. Customer's phone shows the call coming from the Wiom IVR Masked number — not from the CSP user's personal mobile.

Scenarios — and how each is handled

✓ Handled Customer picks up
Both parties talk. The call ends naturally. The call disposition and the recording are saved on the IVR backend.
✓ Handled Customer doesn't pick up
CSP user hears: The customer then receives a push notification on the Customer App:
आपने हमारे टीम का कॉल मिस कर दिया है। कृपया उनसे बात करने के लिए वापस कॉल करें।
When the customer dials back, the flow continues as UC 09 (if they have one active ticket) or UC 10 (multi-ticket).
✓ Handled CSP delays dialling — short-lived in-call mapping expires
If the CSP user opens the dialer but doesn't tap dial within the short TTL window, the seamless-bridge mapping expires. When they eventually do dial, the call falls through to Path 2 and bridges via the identification chain (which still recognises the CSP from sim_inventory). Continues as UC 03 or UC 04. No user-visible failure.
✓ Handled CSP cancels / ends the call themselves before customer picks up
Call doesn't connect. No IVR audio plays — call never reaches the IVR backend. Behaves like any standard outbound call cancel from the phone dialer.

Dialer-initiated callbacks — recognised caller

UC 03 CSP dials back the masked number from their call log — single active ticket
Path 2 ✓ Live

A CSP user previously called a customer via the in-app CTA. Later they want to re-call — they tap the Wiom IVR Masked number entry in their phone's call log. Table 1's TTL has expired so the cached mapping is gone. The IVR recognises their FROM (registered SIM or sim_inventory) and finds exactly one active ticket — bridges directly.

  1. CSP user
    Opens their phone's call log; finds the Wiom IVR Masked number entry; taps dial.
  2. IVR (API 1)
    Looks up FROM in Table 1 → cache miss. Falls back to PIN registry by FROM.
  3. IVR
    Identification chain — first hit: FROM matches a row in sim_inventory → returns the user_id. Finds exactly 1 active ticket for that CSP → directly returns the customer's mobile as the bridge target.
  4. IVR
    Bridges to the customer — no PIN prompt needed.
  5. Customer's phone
    Rings; picks up; call connects.

Edge-case audio (no active ticket)

These audios are tied to the Wiom Call Center / Trust Line numbers (e.g. 8880322222 and the trust-line number), not the IVR Masked number. The IVR Masked number is strictly for customer ↔ partner interaction on an active ticket. When a customer or CSP calls in to the call center / trust line and the IVR cannot find an active ticket against their mobile, it plays the appropriate dead-end message and ends the call.

No active ticket — Customer side
Played on the call center / trust line when a customer's mobile maps to no active Wiom partner ticket.
No active ticket — CSP / Partner side
Played on the call center / trust line when a CSP user's mobile maps to no active ticket.
Call not picked
Played on an IVR Masked number bridge when the dialled party (customer or CSP) doesn't pick up before the timeout — call ends.

The 13 use cases collapse into four distinct routing paths. Each path has its own logic; below is one flowchart per path showing exactly what the IVR does on the call.

Master flow — how the IVR routes any incoming call

Applies to all 13 use cases. Branches into Paths 1–4 based on what's known about the caller.

When a call arrives at the IVR (via the masked number), the very first thing it does is a Table 1 cache lookup. From there, the four paths branch out.

Path 1 — In-app CTA happy path

Covers: UC 01 (CSP from CSP App) · UC 02 (Customer from Customer App)

The user taps the in-app Call CTA on their ticket. The app pre-asks the IVR for the number to dial. The IVR writes a short-TTL mapping into Table 1 and returns the masked number. The user dials it; the IVR recognises the mapping and bridges instantly.

Path 2 — Recognised caller, single active ticket

Covers: UC 03 · UC 05 · UC 07 · UC 09 — every "dial back from call log, exactly one open ticket" scenario.

Table 1 has expired. The IVR runs the identification chain to figure out who's calling. The first step that hits (sim_inventory, Customer API, or Booking API) gives the IVR enough to look up active tickets for the caller. If there's exactly one — bridge directly, no PIN needed.

Audio prompts in this flow

▶ Call not picked
Plays when the bridged counterparty doesn't answer.

Note: the "no active ticket" audios are tied to the Wiom Call Center / Trust Line, not to the IVR Masked number. All 13 UCs assume an active ticket exists; the 0-ticket case isn't a UC branch here.

Path 3 — Recognised caller, multiple active tickets → PIN

Covers: UC 04 · UC 06 · UC 08 · UC 10 — caller is identified but they have 2+ open tickets, so the IVR can't tell which counterparty they want.

The IVR plays the "ask for PIN" audio. The caller reads the PIN from their ticket (in-app card for CSP, SMS or in-app for customer) and enters it. The PIN itself identifies the ticket; the IVR looks up the counterparty's mobile and bridges. Retry policy: on a wrong PIN, the caller is prompted one more time; if the second attempt is also wrong, the call ends. On a timeout (no input), the caller is re-prompted up to three times before the call ends.

Audio prompts in this flow

▶ Ask for PIN
Plays when the IVR needs the caller to enter their 6-digit PIN.
▶ Wrong PIN (1st wrong)
Plays after the first wrong PIN. Caller gets one more chance.
▶ No PIN entered (timeout)
Plays if the caller doesn't enter anything. Re-prompted up to three times.
▶ Limit reached (2nd wrong)
Plays after the second wrong PIN. Call ends.
▶ Call not picked
Plays when the bridged counterparty doesn't answer.

Path 4 — Unknown caller → PIN

Covers: UC 11 (customer from unregistered SIM) · UC 12 (CSP from unregistered SIM) · UC 13 (colleague forwarding).

The caller's mobile fails all three identification lookups — IVR doesn't know who they are. The PIN serves double duty here: it both authenticates the caller (they wouldn't have it unless someone authorised gave it to them) and identifies the ticket they want.

Audio prompts in this flow

▶ Ask for PIN
Plays when the unknown caller is asked to authenticate via PIN.
▶ Wrong PIN (1st wrong)
Plays after the first wrong PIN. Caller gets one more chance.
▶ No PIN entered (timeout)
Plays if the caller doesn't enter anything. Re-prompted up to three times.
▶ Limit reached (2nd wrong)
Plays after the second wrong PIN. Call ends.
▶ Call not picked
Plays when the bridged counterparty doesn't answer.
