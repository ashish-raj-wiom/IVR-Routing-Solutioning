IVR Call Routing — Proposed Design (v1)

Single masked number · 2 entry paths (app / dialer) · 3 tables · PIN fallback · Drafted 2026-05-18

What this solves

  • Single masked number — no MN1/MN2 confusion. Any direction works.
  • Two entry paths — App-initiated (Call CTA) and direct-dial (call log, saved contact) handled by the same routing logic.
  • Happy path unchanged — Table 1 lookup, instant connect.
  • PIN fallback — recovers calls when mapping is stale, FROM is unrecognised, or call comes from the dialer/call log.
  • Customer dialing without prior CTA — handled via the existing Cx ↔ Technician mapping (Table 3).

Use cases

How each path resolves under the new design. The first is the existing happy path (preserved); the rest are the four failure modes the design recovers.

Reference

In-app happy path (preserved)

Works fine today, kept untouched. Partner taps Call CTA in-app from a registered SIM, dials the masked number within TTL.

Instant connect, no PIN. The happy path remains the fastest path.
Use case 01

Partner calls from an unregistered SIM

Partner's SIM isn't in sim_inventory (eSIM, dual-SIM secondary, permission denied, never logged in from this SIM). SIM-detect fails ~30% of the time; call drops.

PIN → customer mobile
    IVR->>C: Bridge to customer
Call connects without needing SIM permissions or app login on this device.
Use case 02

Partner forwards the masked number to a colleague

Partner shares the masked number with a colleague (e.g., a field technician on a different phone). Colleague dials it directly. Their SIM isn't in sim_inventory. Call drops.

Use case 03

Partner dials the masked number from their native dialer

Partner bypasses the app — redials the masked number from call log or a saved contact with no fresh Call CTA. No initiateCall fires; nothing connects today.

Use case 04

Customer calls back the masked number

Customer sees a missed call on the masked number and dials back from their phone's call log. The masked number isn't recognised; call drops.

Tables

TableSchemaSourceLifecycle
Table 1 — Active call mapping FROM list → TO new Written on every initiateCall Short TTL (minutes), GC after expiry
Table 2 — PIN registry customer_mobile → 5-digit PIN new Generated when a ticket opens Per active ticket; GC on ticket closure
Table 3 — Cx ↔ Technician customer_mobile → technician_mobile existing Read from TAS / Connection Lifecycle Maintained by existing systems

Exotel applet wiring

  1. Passthru (Dynamic URL #1) — receives From. Returns either:
    • A direct destination (Table 1 hit or is_customer path), or
    • An instruction to branch to the Gather applet (fallback paths).
  2. Gather / IVR — collects the 5-digit PIN via DTMF.
  3. Connect (Dynamic URL #2) — receives From + digits. Returns destination after Table 2 lookup, or hands off to the "call via app" IVR message.

Telemetry events

Each branch must emit a typed event so failure-mode bucket sizes are visible:

  • mapping_hit — Table 1 happy path
  • is_customer_routed — Table 3 path
  • pin_prompted — Gather applet triggered
  • pin_success / pin_fail
  • api_failure_fallback — Resolve-FROM API down, routed to PIN
  • nudge_to_app — dead-end IVR played

PIN distribution TBD

PIN is issued only on the partner side, per ticket. Channel still to decide:

  • WhatsApp / SMS to the assigned partner-user, OR
  • Surfaced on the ticket card near the Call CTA in the app, OR
  • Both.

Known limitations (v1 will not solve)

  • Customer calling from an unregistered SIM — no PIN held → IVR nudges to call via app.
  • Customer with > 1 active ticket — out of scope. Production reality today is 1 ticket per customer at a time.
  • Dual-role caller (same person both customer and partner-user) — disallowed by the system.
  • PIN brute-force protection — deferred. Good-to-have, not v1.
