IVR Call Routing — Proposed Solution

A meaningful share of partner ↔ customer calls drop today. This is the design that closes the gap.

The problem we're solving

A meaningful share of partner ↔ customer calls fail to connect on Wiom's masked-number infrastructure today. The current design only works in one narrow case: a partner taps the in-app Call CTA from a registered SIM and dials within minutes. Everything else drops silently — partner redialing from a call log, customer returning a missed call, a colleague dialing on the partner's behalf, partner using a SIM the app couldn't detect.

The gap matters because the partner ↔ customer call is load-bearing in every install, service ticket, and router recovery. When the call drops the partner has no fallback — they wait, retry, or escalate; the customer waits with them. Repeated drops translate directly into NPS hits, slot abandonment, and avoidable truck-rolls.

MN1 / MN2 — how masking works today

The current implementation uses two separate masked numbers per call session, one per direction:

MN1
Customer → MN1 → Partner
One-way route. Only customer-initiated calls work.
MN2
Partner → MN2 → Customer
One-way route. Only partner-initiated calls work.

Each is minted via initiateCall when the originating side taps the Call CTA in their app, and bound to a short-lived FROM → TO mapping in the backend. MN1 only knows how to route Customer → Partner; MN2 only the reverse. The masked number is also recycled across sessions — the same physical number is reused across many pairs over time, so a stale number in someone's call log has no guaranteed meaning later.

Where it breaks today

Failure modeWhat happens today
Unregistered / undetected SIM (CSP side) On the CSP side, SIM capture at app login works ~85% of the time. The remaining ~15% (eSIM, dual-SIM secondary slot, READ_PHONE_STATE denied) produce a FROM that isn't in any active mapping. Call drops. (Customer side has no SIM capture at all — only the registered mobile is known, so any call from a different SIM falls through.)
Wrong-direction dial (MN1 ↔ MN2 confusion) Partner sees MN1 in their call log (the number a customer used to call them) and dials it back. MN1 only routes Customer → Partner, so the partner's FROM isn't in the mapping. Call drops.
Native dialer / call-log redial Partner or customer dials the masked number from the phone dialer without a fresh CTA. No initiateCall fires; the mapping has expired (TTL) or never existed for this direction. Call drops.
Customer callback Customer sees a missed call from the masked number and calls back. No live mapping for the customer's FROM. Call drops.
Forwarded masked number Partner shares the masked number with a colleague on chat. Colleague dials from a phone whose SIM isn't in sim_inventory → no mapping. Call drops.
Telemetry gap None of the above failures emit a distinct event. We can't size which bucket is biggest, so any fix today is unprioritised.
Common thread: every failure mode is rooted in the in-app + registered-SIM + fresh-TTL triple. Anything that breaks even one of those three drops the call.

The proposed solution

Replace the two one-way masked numbers (MN1 / MN2) with one bidirectional masked number, backed by a small lookup engine that always tries to identify the caller — and falls back to a 5-digit PIN when it can't.

Three pillars

  1. One masked number per session, not two. Eliminates MN1 ↔ MN2 confusion and turns the partner's call log into something they can actually dial back.
  2. PIN fallback for unrecognised callers. When the caller's number isn't in an active mapping, the IVR asks for a short PIN that the partner received at ticket creation. The PIN unlocks the destination.
  3. Three small tables. Table 1 for the active call mapping (today's behaviour, kept), Table 2 for per-ticket PINs (new), and Table 3 — a customer ↔ technician resolver (also new, because TAS doesn't store customer_mobile; we'll build it by joining TAS with customer-service and expose it via a fast lookup API).

What stays the same

  • The in-app Call CTA still works exactly as today — instant bridge, no PIN, no IVR.
  • Existing telephony provider (Exotel) keeps doing what it does best. We expose two endpoints for the lookup; Exotel does the rest.

What's newly possible

  • Customer who missed a call can dial back from their dialer — bridged to their technician via Table 3, no PIN needed.
  • Partner who switched SIMs, lost the app session, or just prefers their dialer can still place the call by entering their PIN.
  • A partner's colleague can place the call using the same PIN — no new app install required.

Trust layer — recipient-side pickup (already in place)

Routing the call is only half the job; the recipient still has to pick up. Our masked numbers are whitelisted with Truecaller, so the recipient's phone shows a green verified banner with the Wiom name instead of an unknown number or a "Suspected spam" flag. The new single masked number will reuse one of the two existing (already-whitelisted) MN1 / MN2 numbers, so the verified status carries forward as-is — no fresh whitelisting work, no regression on recipient-side trust.

PIN architecture

PIN-based fallback is the standard pattern in double-blind calling systems (Ola, Uber, Swiggy). When the caller's number can't be matched to a recipient, the IVR asks for a short PIN that was pre-shared with the legitimate user — entering it unlocks the destination. In our design the PIN activates whenever Resolve-FROM says "not a customer" (UC01–UC04); customers skip it entirely since Table 3 resolves their technician directly.

PIN distribution — issued per active ticket on the partner side. Primary channel: SMS to the partner-org's Owner / Admin registered mobile at ticket creation (WhatsApp may be sent as a second channel). The ticket card in the app shows the same PIN as reinforcement. The IVR PIN prompt is a reminder of the SMS the caller already received — it does not redirect them to the app.

PIN format (TBD): either the last 5 digits of the ticket ID, or a randomly generated 5-digit value unique across active tickets. UC02 (forwarding to a colleague): the partner forwards the same SMS / WhatsApp message directly to the colleague — it carries the PIN, the masked number, and the ticket details (exact format to be specified by the solution team).

PIN retry policy: capped at 3 attempts per call; on the third wrong entry the call drops to the dead-end IVR (Contact trust line). With a 5-digit space (100,000 combos), 3 tries gives a 0.003% brute-force probability per call — sufficient for this surface.

PIN rotation: PINs rotate daily over the ticket lifetime to limit exposure on multi-day jobs. Each rotation triggers a fresh SMS to the Owner / Admin; the previous PIN expires the moment a new one is issued.

Underlying telephony mechanism: Exotel's Connect Applet with Dynamic URL. Learn more →

Missed-call notifications

Successfully dialling the recipient does not mean the call was picked. Field CSPs are often on rooftops, in cable ducts, or low-signal areas; customers are busy, away, or screening. A missed call without a follow-up is a silent failure — exactly what leadership flagged as the most damaging trust failure mode today.

We close this gap by ingesting Exotel's call-disposition webhook and triggering a CleverTap campaign:

  1. Exotel disposition webhook — Exotel fires a callback for every call with the outcome (answered / no-answer / busy / failed). We listen on this webhook.
  2. Backend → CleverTap event — On any non-answered outcome, the backend fires a typed CleverTap event (e.g. missed_call_partner_to_customer or missed_call_customer_to_partner) with the parties involved.
  3. CleverTap campaign → notification — The campaign sends an SMS / push to the party who missed the call:
    • Customer missed → notify customer ("Your technician tried to reach you. Call back on [number]").
    • CSP missed → notify CSP ("Your customer tried to reach you. Call back on [number]").
IVR language: Hindi. All IVR prompts (PIN entry, dead-end messages, any future menus) and all outbound notification copy default to Hindi, in line with Wiom's voice-first Bharat user. Regional-language expansion based on CSP geography will follow. Exact copy is TBD.
Comms layer dependencies (must land before launch). All outbound SMS — PIN delivery, PIN rotation, missed-call alerts — must be sent via DLT-registered templates with the "Wiom" sender ID, so recipients see "Wiom" as the sender rather than a generic 11444XXXX phone number. WhatsApp comms require the corresponding WhatsApp BSP setup with approved templates.

Exotel applet wiring

  1. Passthru (Dynamic URL #1) — receives From. Returns either:
    • A direct destination (Table 1 hit or is_customer path), or
    • An instruction to branch to the Gather applet (fallback paths).
  2. Gather / IVR — collects the 5-digit PIN via DTMF.
  3. Connect (Dynamic URL #2) — receives From + digits. Returns destination after Table 2 lookup, or hands off to the "call via app" IVR message.

Telemetry events

Each branch must emit a typed event so failure-mode bucket sizes are visible:

  • mapping_hit — Table 1 happy path
  • is_customer_routed — Table 3 path
  • pin_prompted — Gather applet triggered
  • pin_success / pin_fail
  • api_failure_fallback — Resolve-FROM API down, routed to PIN
  • nudge_to_app — dead-end IVR played

Known limitations (out of scope for this build)

  • Customer calling from an unregistered SIM (incl. dual-SIM / family phone) — explicitly out of scope. Falls into the not-customer PIN path; with no PIN held the call ends at the trust-line IVR after 3 attempts.
  • Customer dialing back after their ticket is closed — Table 3 has no active technician → IVR plays "Contact call centre 88803 22222" (no silent drop).
  • Customer with > 1 active ticket — Table 3 returns the most recent ticket (created_at DESC); customer is bridged to that technician.
  • Dual-role caller (same person both customer and partner-user) — disallowed by the system.
