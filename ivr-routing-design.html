IVR Call Routing — Proposed Design (v1)

A meaningful share of partner ↔ customer calls drop today. This is the design that closes the gap.

Drafted 2026-05-18 · For leadership review

The problem we're solving

A meaningful share of partner ↔ customer calls fail to connect on Wiom's masked-number infrastructure today. The current design only works in one narrow case: a partner taps the in-app Call CTA from a registered SIM and dials within minutes. Everything else drops silently — partner redialing from a call log, customer returning a missed call, a colleague dialing on the partner's behalf, partner using a SIM the app couldn't detect.

The gap matters because the partner ↔ customer call is load-bearing in every install, service ticket, and router recovery. When the call drops the partner has no fallback — they wait, retry, or escalate; the customer waits with them. Repeated drops translate directly into NPS hits, slot abandonment, and avoidable truck-rolls.

MN1 / MN2 — how masking works today

The current implementation uses two separate masked numbers per call session, one per direction:

MN1
Customer → MN1 → Partner
One-way route. Only customer-initiated calls work.
MN2
Partner → MN2 → Customer
One-way route. Only partner-initiated calls work.

Each is minted via initiateCall when the originating side taps the Call CTA in their app, and bound to a short-lived FROM → TO mapping in the backend. MN1 only knows how to route Customer → Partner; MN2 only the reverse. The masked number is also recycled across sessions — the same physical number is reused across many pairs over time, so a stale number in someone's call log has no guaranteed meaning later.

Where it breaks today

Failure modeWhat happens today
Unregistered / undetected SIM SIM capture at app login works ~70% of the time. The remaining ~30% (eSIM, dual-SIM secondary slot, READ_PHONE_STATE denied) produce a FROM that isn't in any active mapping. Call drops.
Wrong-direction dial (MN1 ↔ MN2 confusion) Partner sees MN1 in their call log (the number a customer used to call them) and dials it back. MN1 only routes Customer → Partner, so the partner's FROM isn't in the mapping. Call drops.
Native dialer / call-log redial Partner or customer dials the masked number from the phone dialer without a fresh CTA. No initiateCall fires; the mapping has expired (TTL) or never existed for this direction. Call drops.
Customer callback Customer sees a missed call from the masked number and calls back. No live mapping for the customer's FROM. Call drops.
Forwarded masked number Partner shares the masked number with a colleague on chat. Colleague dials from a phone whose SIM isn't in sim_inventory → no mapping. Call drops.
Telemetry gap None of the above failures emit a distinct event. We can't size which bucket is biggest, so any fix today is unprioritised.
Common thread: every failure mode is rooted in the in-app + registered-SIM + fresh-TTL triple. Anything that breaks even one of those three drops the call.

The proposed solution

Replace the two one-way masked numbers (MN1 / MN2) with one bidirectional masked number, backed by a small lookup engine that always tries to identify the caller — and falls back to a 5-digit PIN when it can't.

Three pillars

  1. One masked number per session, not two. Eliminates MN1 ↔ MN2 confusion and turns the partner's call log into something they can actually dial back.
  2. PIN fallback for unrecognised callers. When the caller's number isn't in an active mapping, the IVR asks for a short PIN that the partner received at ticket creation. The PIN unlocks the destination.
  3. Three small tables. One for the active call mapping (today's behaviour), one for per-ticket PINs (new), one read-only customer ↔ technician map (reused from existing systems).

What stays the same

  • The in-app Call CTA still works exactly as today — instant bridge, no PIN, no IVR.
  • Existing telephony provider (Exotel) keeps doing what it does best. We expose two endpoints for the lookup; Exotel does the rest.

What's newly possible

  • Customer who missed a call can dial back from their dialer — bridged to their technician via Table 3, no PIN needed.
  • Partner who switched SIMs, lost the app session, or just prefers their dialer can still place the call by entering their PIN.
  • A partner's colleague can place the call using the same PIN — no new app install required.

PIN architecture — what it is and how we're using it

The general pattern

PIN-based call routing is a fallback used by ride-hail, food delivery, and other double-blind calling systems (Ola, Uber, Swiggy, Amazon Logistics, Dunzo). It works in two layers:

  1. Caller-ID layer (the happy path). When the caller's number matches an active mapping, the system bridges the call instantly. Most calls go through this layer.
  2. PIN layer (the fallback). When the caller's number doesn't match — different SIM, different person, session expired — the IVR asks for a short PIN that was pre-shared with the legitimate user. Enter the right PIN, and the system bridges the call.

The PIN exists for one purpose: to disambiguate who the caller wants to reach when their phone number alone can't tell us.

How it works under the hood

During a fallback call, the telephony provider (Exotel) calls our backend twice:

  1. On ring. Exotel sends the caller's number (FROM) to our backend. The backend decides: bridge directly (caller is recognised) or branch to a PIN prompt.
  2. After PIN entry. Exotel sends the FROM + the digits the user entered. The backend looks up the PIN, resolves the destination, and tells Exotel where to bridge.

This is Exotel's Connect Applet with Dynamic URL pattern — a public, documented mechanism. We don't need to invent telephony; we just expose two endpoints and run lookups fast (< 200 ms) inside Exotel's 5-second timeout budget. Exotel docs →

How we're using it here

The PIN layer activates in three specific scenarios — all of which fail today:

  • Partner calls from an unregistered SIM → unknown FROM → ask for PIN.
  • Partner redials from the dialer / call log → known SIM, but no live mapping → ask for PIN to identify which customer.
  • Colleague dials on the partner's behalf → unknown FROM → ask for PIN.

For customers, we skip the PIN entirely. Today every customer has exactly one active ticket and one assigned technician — so the moment we recognise the customer's FROM, we know who they want to call. No PIN entry, no friction.

PIN distribution TBD

PINs are issued only to the partner side, one per active ticket, valid until the ticket closes. Distribution channel still to decide:

  • WhatsApp / SMS to the assigned partner-user at ticket creation, OR
  • Surfaced on the ticket card near the Call CTA in the app, OR
  • Both.
Comms is a first-class part of this build, not an afterthought. Without reliable PIN delivery the fallback breaks. DLT templates, WhatsApp BSP setup, and missed-call SMS fallbacks all need to land alongside the routing changes.

Tables

TableSchemaSourceLifecycle
Table 1 — Active call mapping FROM list → TO new Written on every initiateCall Short TTL (minutes), GC after expiry
Table 2 — PIN registry customer_mobile → 5-digit PIN new Generated when a ticket opens Per active ticket; GC on ticket closure
Table 3 — Cx ↔ Technician customer_mobile → technician_mobile existing Read from TAS / Connection Lifecycle Maintained by existing systems

Exotel applet wiring

  1. Passthru (Dynamic URL #1) — receives From. Returns either:
    • A direct destination (Table 1 hit or is_customer path), or
    • An instruction to branch to the Gather applet (fallback paths).
  2. Gather / IVR — collects the 5-digit PIN via DTMF.
  3. Connect (Dynamic URL #2) — receives From + digits. Returns destination after Table 2 lookup, or hands off to the "call via app" IVR message.

Telemetry events

Each branch must emit a typed event so failure-mode bucket sizes are visible:

  • mapping_hit — Table 1 happy path
  • is_customer_routed — Table 3 path
  • pin_prompted — Gather applet triggered
  • pin_success / pin_fail
  • api_failure_fallback — Resolve-FROM API down, routed to PIN
  • nudge_to_app — dead-end IVR played

Known limitations (v1 will not solve)

  • Customer calling from an unregistered SIM — no PIN held → IVR nudges to call via app.
  • Customer dialing back after their ticket is closed — Table 3 has no active technician → IVR nudges to call via app (rather than dropping).
  • Customer with > 1 active ticket — out of scope. Production reality today is 1 ticket per customer at a time.
  • Dual-role caller (same person both customer and partner-user) — disallowed by the system.
  • PIN brute-force protection — deferred. Good-to-have, not v1.
